# Architecture Overview

Invoice Management System (Lite)

----

## 1. 本ドキュメントの目的

本ドキュメントは、
Invoice Management System (Lite) における設計方針・構成意図を整理し、
以下を明確にすることを目的としています。

- なぜこの構成・設計にしたのか
- 業務アプリとして何を重視したか
- Lite 版として意図的に省略している点

※ 実装詳細ではなく 設計判断の背景 を中心に記載します。

## 2. システム全体構成
```bash
[ Frontend (Next.js) ]
        |
        |  REST API (JWT)
        |
[ Backend API (ASP.NET Core) ]
        |
        |  ORM (EF Core)
        |
[ PostgreSQL ]
```
### 構成の特徴
- フロントエンド / バックエンド完全分離
- API ベース設計による責務の明確化
- Web 業務アプリとして一般的な三層構成を採用

## 3. ユーザー区分と責務分離
本システムでは 2 種類のユーザー を想定しています。
### 管理者（Admin）
- 全会員・全請求書・全入金を管理
- 請求書発行・編集
- 入金登録・入金割当
- 売上・回収状況の集計確認

### 会員（Member）
- 自身の請求書のみ参照可能
- 支払状況の確認
- 管理操作は不可

## 4. 画面遷移設計（状態遷移図）

画面遷移は以下の考え方で設計しています。
- ログイン後の起点を明確化
- 管理者：管理者ダッシュボード
- 会員：会員用ダッシュボード
- 一覧 → 詳細 → 操作 → 一覧へ戻る、の業務UI基本導線
- 削除・登録後の戻り先を統一し、操作ミスを防止

※ 詳細な遷移は /docs 配下の 状態遷移図 を参照してください。

## 5. データベース設計（ER図）
### 設計方針
- 業務で起こり得る状態変化を正規化して表現
- 一部入金・複数請求対応を最初から考慮
- 集計は保持せず、必要に応じて算出

### 主なテーブル構成

### MEMBERS
- 管理者・会員を統合管理
- Role により権限を判定

### INVOICES
- 請求書の基本情報を保持
- StatusId により現在の請求ステータスを保持
- 入金割当の追加・削除・置き換え時に、割当済み金額からステータスを再計算する
- 表示用定義として InvoiceStatus マスタを参照

### PAYMENTS
- 実際の入金データを保持
- CSV取込・手動登録の両方を想定

### PAYMENT_ALLOCATIONS（重要）
- 1件の入金を複数の請求書に割当可能
- 一部入金・複数請求対応の中核テーブル

### INVOICE_STATUS
- 未入金 / 一部入金 / 入金済み を定義
- 表示順・期限超過判定用フラグを保持

### REMINDER_HISTORIES
- 催促の履歴を保持
- 業務ログとして独立管理

### AUDIT_LOGS
- 管理者操作や重要操作の履歴を保持
- 操作者、操作種別、対象、概要、詳細JSONを記録

### REMINDER_JOBS
- 督促メール等の非同期処理ジョブを保持
- 処理状態、リトライ回数、エラー内容を管理

### PASSWORD_RESET_TOKENS
- パスワード再設定用トークンを保持
- 有効期限と使用済み状態を管理

### PAYMENT_IMPORT_BATCHES
- CSV等から入金データを取り込む場合の取込単位を保持

※ 詳細な関係性は ER図 を参照してください。

## 6. 請求ステータス自動判定ロジック

本システムでは、
請求書に対する入金状況からステータスを自動判定 します。

### 判定方針
- 請求金額合計
- 割当済み入金額合計
を比較し、以下を判定：

| 状態 | 条件 |
| ---- | ---- |
| 未入金 | 割当済み入金額 = 0 かつ支払期限内 |
| 一部入金 | 0 < 割当済み入金額 < 請求金額 |
| 入金済み | 割当済み入金額 >= 請求金額 |
| 期限超過 | 支払期限を過ぎ、未回収額がある |
| キャンセル | 請求自体を無効扱いにする |

キャンセル済み請求書は、自動ステータス再計算の対象外とする。

## 7. API仕様（Swagger / OpenAPI）

本システムのバックエンド API は、
ASP.NET Core による REST API として実装しています。

開発・検証環境では Swagger UI により API 仕様を確認できる構成とする。
本番相当環境では、運用方針に応じて Swagger UI の公開可否を制御する。

今後の改善として、以下を想定しています。

- 開発・検証環境における Swagger（OpenAPI）UI の有効化
- 認証付き API を含めたエンドポイント仕様の可視化
- フロントエンドとの API 契約（I/F）の明確化

## 8. 自動テスト方針

本システムでは、業務上重要なロジック、認証・認可、APIエンドポイント、フロントエンド画面を対象に自動テストを実施しています。

テストは全体網羅ではなく、請求・入金・入金割当・権限分離など、業務上の重要度が高い箇所を優先して整備しています。

### バックエンド単体テスト

- サービス層の業務ロジックを対象にテスト
- 請求書作成・更新時の合計金額再計算
- 入金割当による請求ステータス再計算
- 売上集計、会員管理、認証、督促、監査ログ
- メール送信や監査ログなどの外部依存は Fake / Noop 実装に差し替え

### バックエンド統合テスト

- WebApplicationFactory を使用した API 統合テスト
- JWT 認証、Admin / Member の認可制御
- 401 / 403 / 404 / 400 / 200 / 201 などの HTTP ステータス確認
- Auth、Invoices、Members、Payments、Sales、Collections、OperationLogs などの主要APIを確認

### フロントエンドテスト

- Jest / React Testing Library による画面・コンポーネントテスト
- ログイン、ダッシュボード、請求書、入金、会員、督促画面などの表示・操作を確認

### CI

- GitHub Actions により、push / pull request 時にビルド・テストを自動実行
- フロントエンドは lint / test / build を実行
- バックエンドは restore / build / test を実行


## 9. レイヤードアーキテクチャ

バックエンドは以下の構成を採用しています。
```graphql
Domain
 └─ エンティティ / Enum / ルール

Application
 └─ ユースケース / サービス / DTO

Infrastructure
 └─ DB / 外部サービス / 実装詳細
```

### 意図
- 業務ロジックを Domain / Application に集約
- DB・外部依存を Infrastructure に隔離
- 将来的な変更・拡張に耐えやすい構成

## 10. Lite 版として省略している点
本リポジトリは Lite 版 として、以下を意図的に省略しています。
- 月次締め処理（業務設計の主題から外れるため省略）
- 高度な権限制御（多段ロール）
- 承認フロー（Lite版では単純化を優先）
- 外部決済サービス連携
- 本格的なメール配信運用
  - 請求書送付、配信管理、配信結果管理などは Lite 版では対象外

## 11. 想定ユースケース
- 中小規模事業者向けの請求・入金管理
- Excel 管理からの移行イメージ
- 実務に近い業務フローの再現

## 12. まとめ

本システムは
「学習用アプリ」ではなく「業務アプリ設計の再現」 を目的としています。
- 状態変化を意識した設計
- 一部入金・割当対応
- 実務視点での画面遷移・集計

を重視した構成としています。

## 2. システム化の背景

### 2.1 背景

中小規模事業者における請求・入金管理では、Excelや手作業による管理が行われることが多い。

しかし、請求書、入金情報、入金状況、売上集計、顧客情報が分散して管理されると、以下のような問題が発生しやすい。

- 請求書と入金情報の対応関係が分かりにくい
- 未入金、一部入金、入金済みの状態確認に手間がかかる
- 1件の入金を複数請求書へ割り当てる業務が複雑になる
- 複数回に分けた一部入金の管理が難しい
- 管理者と会員で閲覧・操作できる範囲を分けにくい
- 売上や未回収金額の集計が手作業になりやすい
- 請求書PDFやCSV出力などの帳票処理が後回しになりやすい

本システムは、これらの課題を解決するため、請求・入金・入金割当・売上集計を中心としたWebアプリケーションとして構築する。

### 2.2 現状課題

| No | 課題 | 内容 |
|---:|---|---|
| 1 | 請求・入金情報の分断 | 請求書と入金情報が別々に管理され、入金状況の把握に時間がかかる |
| 2 | 一部入金管理の複雑さ | 請求金額の一部のみ入金された場合、残額管理が煩雑になる |
| 3 | 複数請求への割当 | 1件の入金を複数請求書に割り当てる場合、手作業ではミスが起きやすい |
| 4 | 権限分離の不足 | 管理者と会員で参照・操作範囲を明確に分ける必要がある |
| 5 | 集計作業の属人化 | 月次売上、未入金、回収率などの集計が手作業になりやすい |
| 6 | 帳票・出力作業の負担 | 請求書PDFやCSV出力を手作業で作成する負担がある |
| 7 | 履歴確認の不足 | 督促履歴や操作ログが残らず、後から確認しにくい |

## 3. システム目的

### 3.1 目的

本システムの目的は、請求・入金管理業務において発生しやすい以下の業務をWeb上で一元管理することである。

- 請求書の登録・編集・確認
- 請求書PDFの出力
- 入金情報の登録・確認
- 入金と請求書の割当
- 未入金、一部入金、入金済みの状態確認
- 会員別・年月別の売上集計
- 管理者と会員の権限分離
- 会員自身による請求・支払状況確認

### 3.2 システム化方針

本システムでは、以下の方針で要件を整理する。

| 方針 | 内容 |
|---|---|
| 業務中核への集中 | Lite版として請求・入金・集計の中核機能に絞る |
| 権限分離 | 管理者と会員の操作範囲を明確に分ける |
| 入金割当重視 | 一部入金・複数請求への割当を管理できるようにする |
| 状態管理 | 入金状況に応じて請求ステータスを管理する |
| 業務ロジックの一元化 | 重要な判定はクライアントではなくサーバー側で行う |
| 拡張余地の確保 | 締め処理、自動消込、メール送信などを将来拡張として扱う |

## 4. 想定利用者

### 4.1 利用者区分

本システムでは、以下の利用者を想定する。

| 利用者 | 概要 |
|---|---|
| 管理者 | 請求書、入金、会員、売上集計を管理する利用者 |
| 会員 | 自身の請求書や支払状況を確認する利用者 |

### 4.2 管理者の役割

管理者は、システム全体の業務管理を担当する。

主な役割は以下のとおりである。

- 会員情報を管理する
- 請求書を作成・編集・確認する
- 請求書PDFを出力する
- 入金情報を登録する
- 入金を請求書に割り当てる
- 未入金や一部入金の請求書を確認する
- 督促履歴を記録する
- 売上や回収状況を確認する
- CSV形式で集計結果を出力する
- 管理操作ログを確認する

### 4.3 会員の役割

会員は、自身に関係する請求・支払情報を確認する。

主な役割は以下のとおりである。

- 会員登録を行う
- メール確認を行う
- ログインする
- 自身の請求書一覧を確認する
- 自身の請求書詳細を確認する
- 支払状況を確認する
- 自身の請求書PDFを取得する
- プロフィール情報を確認・更新する
- 必要に応じて退会する

## 5. 対象範囲

### 5.1 対象業務

本システムの対象業務は以下とする。

| 業務 | 内容 |
|---|---|
| 認証・会員登録 | 管理者・会員のログイン、会員登録、メール確認、パスワード再設定 |
| 会員管理 | 会員一覧、検索、詳細確認、編集、無効化 |
| 請求書管理 | 請求書の登録、編集、一覧検索、詳細確認、削除、PDF出力 |
| 入金管理 | 入金の登録、一覧検索、詳細確認 |
| 入金割当 | 入金を請求書に割り当てる |
| 督促管理 | 未入金・期限超過請求に対する督促履歴を記録する |
| 売上集計 | 年月別・会員別に売上や入金状況を集計する |
| CSV出力 | 売上一覧、会員別集計をCSVとして出力する |
| 監査ログ | 管理者操作の履歴を記録・確認する |

### 5.2 対象外範囲

Lite版では、以下の機能は対象外または将来拡張扱いとする。

| 対象外・将来拡張 | 内容 |
|---|---|
| 月次締め処理 | 締め確定、締め後修正制御など |
| 自動入金消込 | 銀行明細CSVや銀行APIからの完全自動照合 |
| 請求書再発行履歴 | 再発行履歴、版管理、再発行理由管理 |
| 税率・消費税詳細管理 | 複数税率、税区分、端数処理の詳細制御 |
| メール自動送信 | 請求書送付、督促メールの自動送信 |
| 多拠点・多組織対応 | 複数会社、部署、拠点単位での管理 |
| 外部会計システム連携 | 会計ソフト、銀行API、外部SaaS連携 |
| 承認ワークフロー | 請求書承認、入金承認、多段承認 |
| 高度な監査機能 | 差分履歴、詳細な操作追跡、承認ログ |

## 6. 業務要件

### 6.1 請求管理要件

| 要件ID | 要件 |
|---|---|
| BR-INV-001 | 管理者は会員に対して請求書を作成できること |
| BR-INV-002 | 請求書は請求番号、請求日、支払期限、請求金額、備考を保持できること |
| BR-INV-003 | 請求書は複数の明細行を保持できること |
| BR-INV-004 | 請求合計金額は明細行の数量と単価から算出できること |
| BR-INV-005 | 管理者は請求書を検索・一覧表示できること |
| BR-INV-006 | 管理者は請求書の詳細を確認できること |
| BR-INV-007 | 管理者は請求書を編集できること |
| BR-INV-008 | 入金割当済みの請求書は不用意に削除できないこと |
| BR-INV-009 | 管理者および会員は請求書PDFを取得できること |
| BR-INV-010 | 会員は自身に紐づく請求書のみ参照できること |

### 6.2 入金管理要件

| 要件ID | 要件 |
|---|---|
| BR-PAY-001 | 管理者は会員に紐づく入金情報を登録できること |
| BR-PAY-002 | 入金情報は入金日、入金額、振込名義、入金方法を保持できること |
| BR-PAY-003 | 管理者は入金情報を検索・一覧表示できること |
| BR-PAY-004 | 管理者は入金詳細を確認できること |
| BR-PAY-005 | 入金には未割当、部分割当、割当済みの状態を表示できること |
| BR-PAY-006 | 入金額、割当済み金額、未割当金額を確認できること |

### 6.3 入金割当要件

| 要件ID | 要件 |
|---|---|
| BR-ALC-001 | 管理者は1件の入金を1件または複数の請求書に割り当てられること |
| BR-ALC-002 | 1件の請求書に対して複数回の入金割当を行えること |
| BR-ALC-003 | 割当金額は0より大きい金額であること |
| BR-ALC-004 | 割当合計金額は入金金額を超えないこと |
| BR-ALC-005 | 割当追加・削除・更新後に請求ステータスを再判定できること |
| BR-ALC-006 | 同一入金と同一請求書の重複割当を防止できること |
| BR-ALC-007 | 割当済み金額と請求金額から未回収額を算出できること |

### 6.4 請求ステータス要件

| 要件ID | 要件 |
|---|---|
| BR-STS-001 | 請求書は未入金、一部入金、入金済み、期限超過、キャンセルの状態を扱えること |
| BR-STS-002 | 入金割当がない請求書は未入金として扱えること |
| BR-STS-003 | 割当済み金額が請求金額未満の場合、一部入金として扱えること |
| BR-STS-004 | 割当済み金額が請求金額以上の場合、入金済みとして扱えること |
| BR-STS-005 | 支払期限を過ぎ、未回収額がある場合、期限超過として扱えること |
| BR-STS-006 | キャンセル済み請求書は自動再計算の対象外とできること |

### 6.5 督促管理要件

| 要件ID | 要件 |
|---|---|
| BR-REM-001 | 管理者は請求書に対して督促履歴を登録できること |
| BR-REM-002 | 督促履歴には督促日時、方法、タイトル、メモ、次回対応日を記録できること |
| BR-REM-003 | 請求書詳細画面で督促履歴を確認できること |
| BR-REM-004 | 期限超過や未入金の請求書を督促対象として扱えること |

## 10. 権限要件

### 10.1 ロール

本システムでは以下のロールを扱う。

| ロール | 内容 |
|---|---|
| Admin | 管理者 |
| Customer / Member | 一般会員 |
| Disabled | 退会・無効状態 |

### 10.2 権限制御方針

| 項目 | 要件 |
|---|---|
| 管理者機能 | Adminのみ利用可能とする |
| 会員機能 | ログイン済み会員が自身の情報のみ利用可能とする |
| 請求書参照 | 管理者は全件、会員は自身の請求書のみ参照可能とする |
| 入金管理 | 管理者のみ登録・割当可能とする |
| 売上集計 | 管理者のみ利用可能とする |
| PDF出力 | 管理者は全請求書、会員は自身の請求書のみ出力可能とする |
| 退会済み会員 | ログインや通常操作の対象外とする |

### 10.3 API認可要件

- APIレベルで管理者・会員の権限制御を行うこと
- フロントエンドの画面制御だけに依存しないこと
- 会員が他会員の請求書や入金情報を参照できないこと
- 管理者専用APIに会員トークンでアクセスした場合は拒否すること

## 14. 制約事項・前提条件

### 14.1 技術的前提

| 項目 | 内容 |
|---|---|
| フロントエンド | Next.js / TypeScript / Tailwind CSS |
| バックエンド | ASP.NET Core / .NET 10 / Minimal API |
| データベース | PostgreSQL 16 |
| ORM | Entity Framework Core |
| 認証 | JWT |
| PDF出力 | QuestPDF |
| CI | GitHub Actions |
| デプロイ | ConoHa VPS / Docker Compose / nginx / Vercel / Azure Static Web Apps |

### 14.2 業務的前提

- Lite版として、中小規模事業者の請求・入金管理を想定する
- 管理者は少人数での利用を想定する
- 会員は自身の請求書と支払状況を確認する利用者とする
- 入金データは主に手動登録を想定する
- 自動入金消込や外部会計連携は将来拡張とする
- 月次締めや承認フローはLite版では対象外とする

### 14.3 運用上の前提

- 2026年8月にバックエンド API / PostgreSQL を Heroku から ConoHa VPS へ移行している
- バックエンド API は `https://api.oybusin.com` で公開する
- VPS 上では Docker Compose により ASP.NET Core API、PostgreSQL 16、nginx を運用する
- nginx をリバースプロキシとして利用し、Let's Encrypt / Certbot により HTTPS 化する
- PostgreSQL のデータは Docker Volume に永続化する
- フロントエンドは Vercel / Azure Static Web Apps を公開・検証環境として利用する
- Health Check により VPS 上の API 稼働状態を確認できること
- Swagger UI は本番相当環境で動作確認に利用できる構成とする
- DB バックアップは VPS 側で PostgreSQL データを保全できる運用とする

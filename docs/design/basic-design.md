# Invoice Management System Lite 基本設計書

## 1. システム概要

### 1.1 システム名

Invoice Management System Lite

### 1.2 システムの目的

本システムは、中小規模事業者における請求・入金管理業務を想定した業務向け Web アプリケーションである。

請求書の発行、入金登録、入金割当、入金状況の確認、売上集計、PDF 出力、CSV 出力など、請求・入金管理における中核的な業務を Web 上で管理できるようにすることを目的とする。

従来、Excel や手作業で管理されがちな請求情報・入金情報を一元管理し、管理者と会員で操作可能な範囲を分離することで、業務の見通しやすさ、安全性、保守性を高める。

### 1.3 システムの背景

請求・入金管理業務では、以下のような課題が発生しやすい。

- 請求書と入金情報が別々に管理され、入金状況の確認に手間がかかる
- 一部入金や複数請求への入金割当など、Excel では管理が複雑になりやすい
- 管理者と会員で参照・操作できる情報を分ける必要がある
- 月次売上や未入金状況の集計が手作業になりやすい
- PDF 出力や CSV 出力など、帳票・集計業務が後回しになりやすい

本システムでは、請求書、入金、入金割当を中心としたデータ設計を行い、入金状況をシステム上で一貫して確認できる構成とする。

### 1.4 システムの特徴

| 項目 | 内容 |
|---|---|
| 権限分離 | 管理者と会員を分離し、API レベルで操作範囲を制御する |
| 請求管理 | 請求書の一覧、詳細、登録、編集、削除、PDF 出力を行う |
| 入金管理 | 入金情報の登録、詳細確認、請求書への割当を行う |
| 入金ステータス管理 | 入金履歴・入金割当をもとに、未入金・一部入金・入金済みを判定する |
| 売上集計 | 年月・会員単位で売上や回収状況を確認する |
| CSV 出力 | 売上一覧、会員別売上集計を CSV として出力する |
| PDF 出力 | 請求書を PDF として出力する |
| 監査ログ | 管理者操作や重要操作を後から確認できる余地を持つ |

## 3. システム構成

### 3.1 全体構成

本システムは、フロントエンドとバックエンドを分離した Web アプリケーション構成とする。

```text
[ Frontend: Next.js ]
        |
        | REST API / JWT
        |
[ Backend API: ASP.NET Core ]
        |
        | Entity Framework Core
        |
[ Database: PostgreSQL ]
```

### 3.2 構成要素

| 区分 | 技術 | 主な責務 |
|---|---|---|
| フロントエンド | Next.js / TypeScript / Tailwind CSS | 画面表示、入力受付、画面遷移、API 呼び出し |
| バックエンド API | ASP.NET Core / .NET 8 / Minimal API | 認証・認可、業務ロジック、データアクセス、PDF・CSV 生成 |
| データベース | PostgreSQL | 会員、請求書、入金、入金割当、督促履歴、監査ログの保持 |
| ORM | Entity Framework Core | エンティティと DB テーブルの対応、リレーション、制約管理 |
| 認証方式 | JWT | ログイン後の認証、API アクセス制御 |
| PDF 出力 | QuestPDF | 請求書 PDF の生成 |
| CI | GitHub Actions | フロントエンド・バックエンドのビルド、単体テスト、統合テスト、継続的検証 |
| デプロイ | Heroku / Azure Static Web Apps | 本番相当環境、UI ホスティング検証 |

### 3.3 レイヤー構成

バックエンドは、業務ロジックと外部依存を分離するため、以下のレイヤー構成とする。

```text
Domain
 └─ エンティティ / Enum / 業務ルール

Application
 └─ ユースケース / サービスインターフェース / DTO

Infrastructure
 └─ DB アクセス / PDF 生成 / 外部サービス実装

API
 └─ エンドポイント / 認証・認可 / DI 設定
```

### 3.4 レイヤー分離の方針

| レイヤー | 方針 |
|---|---|
| Domain | 請求、入金、会員などの業務概念を表現する |
| Application | 業務ユースケースとサービスインターフェースを定義する |
| Infrastructure | EF Core、PDF 生成、メール送信などの実装詳細を担当する |
| API | HTTP リクエストを受け取り、認証・認可後に Application 層へ処理を委譲する |
| Frontend | 画面表示とユーザー操作に専念し、業務判定はバックエンドへ委譲する |

## 4. 利用者・権限設計

### 4.1 利用者区分

本システムでは、管理者と会員を同一の `Members` テーブルで管理し、`Role` により権限を区分する。

| Role | 名称 | 内容 |
|---:|---|---|
| 1 | Admin | 管理者。全体管理機能を利用できる |
| 2 | Customer | 一般会員。自身に紐づく情報のみ参照・更新できる |
| 9 | Disabled | 退会・無効化済み。ログインや通常操作の対象外 |

### 4.2 管理者の操作範囲

管理者は以下を操作可能とする。

- 全会員の一覧・詳細確認
- 会員情報の編集・無効化
- 全請求書の登録・編集・削除・PDF 出力
- 全入金の登録・確認
- 入金割当の登録・変更・削除
- 督促履歴の登録・確認
- 売上一覧、会員別売上集計の確認
- CSV 出力
- 管理者操作ログの確認

### 4.3 会員の操作範囲

会員は以下を操作可能とする。

- 自身の請求書一覧の確認
- 自身の請求書詳細の確認
- 自身の請求書 PDF の取得
- 自身の支払状況の確認
- 自身のプロフィール確認・更新
- 退会操作

会員は他会員の請求書、入金情報、売上集計、管理者向け画面にはアクセスできない。

### 4.4 認可方針

認可はフロントエンドの表示制御だけに依存せず、バックエンド API 側で必ず実施する。

| 区分 | 方針 |
|---|---|
| 管理者専用 API | Admin ロールのみ許可する |
| 会員向け API | ログイン会員本人のデータのみ許可する |
| 共通 API | 認証済みユーザーのみ許可する |
| 未認証 API | ログイン、会員登録、メール確認、パスワード再設定などに限定する |

## 6. 画面設計

### 6.1 画面設計方針

画面は、業務アプリとしての一覧性、検索性、誤操作防止を重視する。

- ログイン後の起点を管理者・会員で分離する
- 一覧 → 詳細 → 操作 → 一覧へ戻る、の導線を基本とする
- 登録・編集・削除後の戻り先を明確にする
- 管理者と会員で見える画面を分離する
- 業務上重要な操作は詳細画面から実行する

## 7. データ設計概要

### 7.1 データ設計方針

本システムでは、請求・入金管理業務に必要な情報を、会員、請求書、請求明細、入金、入金割当、督促履歴、監査ログに分けて管理する。

特に入金ステータスについては、単純なフラグのみで管理するのではなく、請求書に対する入金割当情報をもとに判定できる構成とする。

これにより、以下の業務ケースに対応する。

- 1 件の請求書に対して一部入金がある
- 1 件の入金を複数の請求書に割り当てる
- 入金割当を追加・削除し、請求状態を再計算する
- 未入金、一部入金、入金済み、期限超過などの状態を管理する
- 督促履歴や操作ログを後から確認できるようにする

### 7.2 主要テーブル一覧

| テーブル名 | 概要 |
|---|---|
| Members | 管理者・会員情報を管理する |
| Invoices | 請求書ヘッダ情報を管理する |
| InvoiceLines | 請求書明細を管理する |
| InvoiceStatuses | 請求ステータスのマスタを管理する |
| Payments | 入金情報を管理する |
| PaymentAllocations | 入金と請求書の割当情報を管理する |
| PaymentImportBatches | 入金取込単位を管理する |
| ReminderHistories | 督促履歴を管理する |
| PasswordResetTokens | パスワード再設定トークンを管理する |
| AuditLogs | 管理者操作などの監査ログを管理する |

### 7.3 主なリレーション

```text
Member 1 ── * Invoice
Member 1 ── * Payment

Invoice 1 ── * InvoiceLine
Invoice 1 ── * PaymentAllocation
Invoice 1 ── * ReminderHistory

Payment 1 ── * PaymentAllocation

PaymentImportBatch 1 ── * Payment

InvoiceStatus 1 ── * Invoice
```

### 7.4 入金割当設計

入金管理の中核は `PaymentAllocation` である。

`Payment` は実際に入金された金額を表し、`Invoice` は請求書を表す。`PaymentAllocation` は、どの入金をどの請求書にいくら割り当てたかを表す中間テーブルである。

この設計により、以下を実現する。

- 1 件の入金を複数の請求書へ割り当てる
- 1 件の請求書に複数回の入金を割り当てる
- 入金割当を後から修正する
- 入金額、割当額、未割当額を別々に管理する
- 請求書単位の残額を再計算する

## 8. 業務ロジック概要

### 8.1 業務ロジック設計方針

本システムでは、画面や API エンドポイントに業務判断を直接記述せず、主な業務処理を Service 層に集約する。

フロントエンドは入力・表示・画面遷移を担当し、以下のような業務上重要な判断はバックエンドで行う。

- 請求合計金額の計算
- 入金済み金額の集計
- 請求ステータス判定
- 入金割当の妥当性確認
- 権限によるアクセス制御
- 削除可否判定

### 8.2 請求ステータス判定

請求書の入金状況は、請求金額と割当済み入金額の関係から判定する。

| ステータス | 判定条件 |
|---|---|
| 未入金 | 割当済み入金額 = 0 かつ支払期限内 |
| 一部入金 | 0 < 割当済み入金額 < 請求金額 |
| 入金済み | 割当済み入金額 >= 請求金額 |
| 期限超過 | 割当済み入金額 = 0 かつ支払期限を過ぎている |
| キャンセル | 請求自体を無効扱いにする |

請求ステータスは、入金割当の追加、変更、削除時に再計算する。

### 8.3 請求書登録・編集

請求書登録・編集では、請求ヘッダと請求明細を扱う。

- 会員が存在することを確認する
- 請求明細の表示順を整える
- 請求合計金額はクライアント入力に依存せず、サーバー側で再計算する
- 入金済みまたはキャンセル済みの請求書は編集制限を設ける
- 入金割当が存在する請求書は削除不可とする

### 8.4 入金登録・入金割当

入金登録では、会員、入金日、入金額を検証し、入金情報を登録する。

入金割当では、以下を検証する。

- 入金が存在すること
- 請求書が存在すること
- 割当金額が 0 より大きいこと
- 割当合計が入金額を超えないこと
- 同一入金と同一請求書の重複割当を防止すること

入金割当の追加・変更・削除後は、対象請求書のステータスを再計算する。

### 8.5 督促管理

督促管理では、未入金または期限超過の請求書に対して、督促履歴を登録する。

督促履歴には、督促日時、方法、文面トーン、タイトル、メモ、次回対応日、件名、本文などを保持する。

### 8.6 会員退会・無効化

会員の退会・無効化は、物理削除ではなく論理的な無効化として扱う。

- `IsActive = false` とする
- `Role = Disabled` とする
- 過去の請求書・入金履歴との整合性は維持する
- 無効化後はログインや通常操作の対象外とする

### 8.7 監査ログ

重要な管理操作については、監査ログとして記録する。

記録対象の例は以下のとおりである。

- 請求書登録・編集・削除
- 入金登録
- 入金割当追加・変更・削除
- 会員編集・無効化
- 督促履歴登録

監査ログには、操作者、操作内容、対象エンティティ、対象 ID、概要、詳細 JSON、IP アドレス、UserAgent などを保持できる構成とする。

## 9. 外部インターフェース概要

### 9.1 API 方式

フロントエンドとバックエンドは REST API により通信する。

| 項目 | 内容 |
|---|---|
| 通信方式 | HTTP / HTTPS |
| データ形式 | JSON |
| 認証方式 | JWT |
| 認可方式 | Role / Owner 判定 |
| エラー形式 | HTTP ステータスコード + エラーメッセージ |

### 9.2 主な API 分類

| 分類 | 概要 |
|---|---|
| Auth API | ログイン、会員登録、メール確認、パスワード再設定 |
| Admin API | 管理者ダッシュボード、操作ログ取得 |
| Members API | 会員一覧、会員詳細、会員編集、無効化 |
| Invoices API | 請求書一覧、詳細、登録、編集、削除、PDF 出力 |
| Payments API | 入金一覧、登録、詳細、入金割当 |
| Collections API | 督促対象確認、督促履歴登録 |
| Sales API | 売上一覧、会員別売上集計、CSV 出力 |

### 9.3 認証・認可 API 方針

- ログイン成功時に JWT を発行する
- JWT にはユーザー ID と Role を含める
- 管理者専用 API は Admin ロールを必須とする
- 会員向け API はログイン会員本人のデータのみ参照可能とする
- フロントエンド側の画面制御とは別に、API 側でも必ず認可を行う

## 10. 帳票・ファイル出力設計

### 10.1 PDF 出力

請求書 PDF はバックエンド API 側で生成する。

| 項目 | 内容 |
|---|---|
| 出力対象 | 請求書 |
| 出力形式 | PDF |
| 生成方式 | QuestPDF |
| 利用者 | 管理者、会員 |
| 認可 | 管理者は全請求書、会員は自身の請求書のみ出力可能 |

PDF 出力では、日本語表示を考慮し、環境差による文字化けを防ぐため、フォントの扱いに注意する。

### 10.2 CSV 出力

売上一覧および会員別売上集計は CSV として出力する。

| 出力 | 内容 |
|---|---|
| 売上一覧 CSV | 請求書単位の売上・入金状況を出力する |
| 会員別売上集計 CSV | 会員単位の請求額、入金額、未回収額を出力する |

CSV 出力は、管理者向け機能として提供する。

## 11. 非機能設計

### 11.1 セキュリティ

| 項目 | 方針 |
|---|---|
| 認証 | JWT によりログイン状態を管理する |
| 認可 | Role と所有者判定により API アクセスを制御する |
| パスワード | ハッシュ化して保存する |
| メール確認 | 会員登録後、メール確認トークンにより確認する |
| パスワード再設定 | 再設定トークンと有効期限により制御する |
| CORS | 許可されたフロントエンド URL のみ通信を許可する |

### 11.2 入力チェック

入力チェックは、フロントエンドとバックエンドの両方で行う。

ただし、業務上重要な検証はバックエンドを正とする。

| 対象 | 主な検証 |
|---|---|
| ログイン | メールアドレス、パスワード必須 |
| 会員登録 | 氏名、メールアドレス、パスワード必須 |
| 請求書 | 会員、請求日、支払期限、明細、金額 |
| 入金 | 会員、入金日、入金額 |
| 入金割当 | 入金、請求書、割当金額、割当合計 |

### 11.3 エラーハンドリング

| 種別 | 方針 |
|---|---|
| 入力エラー | 400 Bad Request として扱う |
| 未認証 | 401 Unauthorized として扱う |
| 権限不足 | 403 Forbidden として扱う |
| 対象なし | 404 Not Found として扱う |
| 業務制約違反 | 400 または 409 として扱う |
| サーバーエラー | 500 Internal Server Error として扱う |

### 11.4 ログ・監査

- 管理者操作や入金割当などの重要操作は監査ログとして記録する
- API エラーや例外は原因調査が可能な形でログ出力する
- 個人情報やパスワードなどの機密情報はログに出力しない

### 11.5 日時管理

日時はサーバー側で UTC を基本として扱う。

DB 保存時には DateTime の Kind を確認し、必要に応じて UTC に正規化する。

### 11.6 パフォーマンス・拡張性

Lite 版として大規模処理は対象外だが、以下を考慮する。

- 会員 ID、請求書 ID、入金 ID、日付、ステータスに対する検索性
- 請求書一覧、入金一覧、売上一覧のページングまたは条件検索
- 集計値は必要に応じて算出し、過度な重複保持を避ける
- 将来的なモバイルアプリや別クライアント追加を考慮し、API ベースで設計する

## 12. テスト設計概要

### 12.1 テスト方針

本システムでは、業務上重要なロジック、認証・認可、画面遷移、PDF 出力、CSV 出力を中心にテストする。

バックエンドでは、サービス層の業務ロジックを確認する単体テストと、API・認証・認可・DB 接続を含めて確認する統合テストを実施する。

フロントエンドでは、画面表示、ユーザー操作、API 通信時の正常系・異常系表示を中心に確認する。

テストは全体網羅よりも、業務リスクが高い箇所を優先する。

### 12.2 バックエンドテスト

バックエンドテストでは、サービス層の業務ロジックを確認する単体テストと、API エンドポイントを HTTP 経由で確認する統合テストを実施する。

| 分類 | 対象 | 内容 |
|---|---|---|
| 単体テスト | Service 層 | 請求書、入金、入金割当、売上集計、会員、認証、督促、監査ログなどの業務ロジックを確認する |
| 単体テスト | 業務ロジック | 合計金額再計算、入金割当、ステータス再計算、検索、集計、外部依存の差し替えを確認する |
| 統合テスト | Auth API | ログイン、JWT 発行、未確認メール、認証エラーを確認する |
| 統合テスト | Admin / Members API | 管理者専用 API、会員一覧、会員詳細、権限不足、NotFound を確認する |
| 統合テスト | Invoices API | 請求書詳細、所有者判定、管理者検索、未認証、権限不足を確認する |
| 統合テスト | Payments API | 入金一覧、入金登録、バリデーションエラー、AdminOnly 制御を確認する |
| 統合テスト | Sales API | 売上一覧、会員別集計、CSV 出力、AdminOnly 制御を確認する |
| 統合テスト | Collections API | 督促対象確認、督促履歴取得、督促履歴登録、AdminOnly 制御を確認する |
| 統合テスト | OperationLogs API | 操作ログ一覧、直近ログ、AdminOnly 制御を確認する |

### 12.3 フロントエンドテスト

| 対象 | 内容 |
|---|---|
| ログイン画面 | 入力、エラー表示、遷移 |
| 管理者画面 | 一覧、詳細、登録、編集導線 |
| 会員画面 | 自分の請求書一覧、プロフィール画面 |
| API 通信 | 正常系、異常系の表示 |
| 権限制御 | Role による表示切替、遷移制御 |

### 12.4 結合テスト

本節の結合テストは、フロントエンドを含む画面操作ベースの確認を指す。
バックエンド API 単体の統合テストについては、12.2 のバックエンドテストで扱う。

結合テストでは、フロントエンド、バックエンド API、DB、認証、権限、PDF 出力、CSV 出力が連携して動作することを確認する。

特に以下を重点確認する。

- 管理者ログイン後、管理者画面を操作できること
- 会員ログイン後、自身の情報のみ確認できること
- 管理者専用 API に会員がアクセスした場合、拒否されること
- 請求書登録から入金割当、ステータス更新まで一連の業務が成立すること
- PDF 出力で日本語が正常に表示されること
- 本番相当環境で API 通信が成立すること

## 14. 運用設計概要

### 14.1 基本運用

- 管理者が会員、請求書、入金、売上集計を管理する
- 会員は自身の請求書と支払状況を確認する
- 重要操作は監査ログとして保存する
- 本番相当環境では Health Check により API 稼働を確認する

### 14.2 バックアップ・データ管理

- DB はマネージド DB のバックアップ機構を利用する想定とする
- EF Core Migrations により DB 差分を管理する
- 完成 SQL ファイルを手動管理するのではなく、Migration を正とする

### 14.3 障害時の確認観点

| 事象 | 確認観点 |
|---|---|
| ログイン不可 | API 稼働、JWT 設定、DB 接続、メール確認状態 |
| 一覧表示不可 | API URL、CORS、認証 Cookie、検索条件 |
| PDF 出力不可 | API ルート、認可、PDF 生成処理、フォント |
| ステータス不整合 | 入金割当、請求金額、ステータス再計算 |
| CSV 出力不可 | 集計 API、認可、レスポンス形式 |
